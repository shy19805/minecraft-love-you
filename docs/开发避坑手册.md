# 我的世界爱你（Minecraft Love You）— 26.2 开发避坑手册

> 本文档记录本项目实际踩过的坑。**每次修一个新坑，必须追加到这里**（格式见末尾）。
> AI/开发者动手前先通读一遍，防重蹈覆辙。

---

## 1. 专服/客户端类泄漏（致命）

**症状**：单机正常，专服启动即崩：
```
Cannot load class net.minecraft.client.gui.components.events.ContainerEventHandler in environment type SERVER
```
**根因**：被服务端 tick/事件回调触达的类（如配置类）import 了客户端类（Screen / Cloth Config）。
**规则**：
- 配置拆两层：`WlyConfigData`（纯 Gson 数据层，服务端安全）+ `WlyConfig`（仅 GUI）。
- `ModuleManager.enabled()` 只引用数据层。
- **任何被 ServerTick / 事件回调触达的类，不得 import 客户端类**。

## 2. 26.2 配方 JSON 格式

`crafting_shapeless` 的 `ingredients` 是**纯字符串数组**：
```json
"ingredients": ["minecraft:milk_bucket", "minecraft:gunpowder"]
```
不是 `{"item":...}` 也不是 `{"id":...}`。写配方前先 `unzip -p mc.jar data/minecraft/recipe/xxx.json` 抄原版同类型格式。
**验证**：启动日志 `Loaded N recipes` 数量比对（+1 = 加载成功），无 `Couldn't parse`。

## 3. 方块移除钩子改名

26.2：`onRemove` → **`affectNeighborsAfterRemoval(BlockState, ServerLevel, BlockPos, boolean)`**。
（墓碑破坏掉物品当初用 onRemove → 编译期才暴露。）

## 4. 模型 texture_size / UV 网格（踩了两次！）

- **element faces 的 uv 数值永远是 0~16、相对整张纹理**。
- `texture_size:[64,64]` 只是声明"这张图按 64 网格细分"，**不是**"uv 写像素坐标"。
- 64×64 贴图取半张 → uv `[0,0,8,8]`；32×32 纹理在同模型混用时 → uv 坐标 ÷2。
- 踩坑记录：先写成像素坐标（只显示纹理角块），又 ×2（烘焙越界崩溃 `translucency out of bounds`）。

## 5. 部署铁律（踩了两次！）

**改码 → 必须 `gradlew build` → 再复制 jar → `Get-FileHash` 对比源/目标 MD5 一致才算部署**。
`runServer` 只编译运行不产 jar——上次直接 Copy 旧 jar 导致"修复了但用户拿到的还是旧行为"。

## 6. 26.2 模组快捷键

- `new KeyMapping(...)` **不会**进 `Options.keyMappings[]` → 按键设置看不到/不能改/不存档。
- 必须 `KeyMappingHelper.registerKeyMapping(...)`（fabric-key-mapping-api-v1，包 `...client.keymapping.v1`）。
- 键名用翻译键 `key.<ns>.<id>`，分类语言键 `key.category.<ns>.<path>`，lang 必须补齐。
- **注册代码必须真的存在**——曾有一次 sed 批量替换把 2 行 register 写丢（锚点匹配旧文本但替换文本漏行），快捷键全无效。

## 7. mixins.json 子包路径（preLaunch 即崩）

client/mixins 段的名字是**相对 package 的路径**：位于子包必须写 `"client.XxxMixin"`，只写短名 → ClassNotFoundException → 启动崩。
**发布前脚本核对**：mixins.json 每一项 ↔ jar 内 class 路径一一对应（tools 已有做法）。

## 8. @Shadow 只认目标类自身声明的字段

- 父类字段（hoveredSlot/leftPos/topPos）→ mixin 挂**父类** + `instance-of` 过滤子类。
- 祖父类字段（Screen.font）→ 不用 @Shadow，改公共 getter（`getFont()`）。
- 否则打开任意容器屏（26.2 会预加载全部屏幕类）即 APPLY 崩溃。

## 9. 26.2 屏幕点击新签名

```java
mouseClicked(MouseButtonEvent event, boolean doubleClick, CallbackInfoReturnable<Boolean>)
// event.x() / event.y() / event.button()
```
旧 `(double,double,int,CallbackInfo)` 签名 → InvalidInjectionException 崩（打开容器屏时）。

## 10. mixin ordinal：先 javap -c 数调用序

带 `ordinal = N` 的注入必须先 `javap -c` 数目标方法里的调用序（例：FoodData 的 clamp 在私有 `add(IF)V` 里且只有一处；AnvilMenu.createResult 里 hasInfiniteMaterials 有 2 处，too-expensive 是 ordinal=1）。
**教训**：`runServer 绿 ≠ 进世界绿`——FoodData 只在玩家入世界时才触发注入，无玩家的启动验证是假绿。

## 11. 事件/字段访问的编译器陷阱

- protected 方法跨类调用 → 用 `@Invoker` mixin（例：`AbstractVillager.addOffersFromTradeSet`）。
- `ServerPlayer.serverLevel()` 26.2 无此方法 → `(ServerLevel) player.level()`。
- 容器拿物品：`Container` 无 `getItems()` → 逐槽 `menu.getSlot(i).getItem()`。
- `ItemStack.getUseDuration` 等方法引用主机类要写对（`RevealPayload::write` 不是 `WlyNet::write`）。

## 12. 文件编码（GBK 污染）

pwsh `Set-Content/Get-Content` 读写含中文的源码会变 GBK → javac 报"未结束的字符串文字"。
**规则**：改含中文的 .java/.json 一律用 python `io.open(..., encoding='utf-8')` 或 write/edit 工具；pwsh 只做无中文的 sed 类操作。

## 13. 功能验证不充分 = 假交付（反复发生的元问题）

历史教训链：墓碑没存物品（事件时序）→ 连锁只遍历命中数不限制遍历数（卡死）→ 过滤器用错方块类型（所有作物不生效）→ reveal tooltip 依赖 hoveredSlot（按钮区恒 null）→ 村民只改渲染不改数据（列表不全）→ reroll 只做服务端没做触发入口（无按钮无键）。
**规则**：每个功能交付前对照用户验收口径逐条走一遍"触发路径是否真实可达"；mixin 类功能必须确认**注入点真的会执行**（有玩家/有界面的场景）。

## 14. 26.2 字段搬家：invulnerableTime 在 Entity（崩启动）

@Accessor("invulnerableTime") 挂 LivingEntity → No candidates were found → 启动崩。
26.2 该字段（还有大量通用字段）已上移到父类 `Entity`（public int）。**@Accessor/@Shadow 一样只认目标类自身字段**——先 `javap -p 目标类 | grep 字段`，找不到就逐级上父类找，挂对应层级。

## 15. 部署坑复发警告（本条 = 防复发）

"runServer 验证通过"后**立即部署旧 jar** 的错误已发生两次。流程必须硬性串行：
build（产 jar）→ Copy → Get-FileHash 双端一致 → 才算交付。任何一步顺序颠倒/省略 = 交付旧代码。

## 16. InventoryMenu 槽位常量陷阱：INV_SLOT_START..END **包含**快捷栏

主背包段 = `INV_SLOT_START .. USE_ROW_SLOT_START`（不含快捷栏），快捷栏 = `USE_ROW..END`。
按"START..END 一整段"遍历会把快捷栏**收进背包重排**（还会重复收集导致串位）。

## 17. 方块模型禁用 translucent 渲染层（透视元凶）

`render_type: minecraft:translucent` 的模型：半透层**不做不透明深度写入**，模型内部 box 相邻面叠加处呈透明透视。给"烟/雾"半透元素时**不要**把整个模型挂 translucent——烟雾改用 cutout（alpha 二值）+ 碎孔淡灰像素做伪半透。元素间重叠面还要逐一删除被遮面（down/up 贴合面）防 z-fight。

## 18. 26.2 世界渲染（B4 渲染三项的实现路径）

- 世界内绘制挂 fabric `LevelRenderEvents.COLLECT_SUBMITS`，回调参数 `LevelRenderContext` 提供
  `submitNodeCollector()`（OrderedSubmitNodeCollector）与 `poseStack()`；相机位置取
  `mc.gameRenderer.mainCamera().position()`（**不是** getMainCamera/getPosition）。
- 自定义几何：`collector.submitCustomGeometry(poseStack, RenderTypes.LINES, (pose, vc) -> {...})`，
  顶点用 `vc.addVertex(pose.pose(), x,y,z).setColor(r,g,b,a)`。
- 光柱用 4 根竖线（LINES），弹道虚线同；血条做 HUD（HudElementRegistry.addLast，fill 用 RenderPipelines.GUI）。
- 其它易错：`mc.options.hideGui` 不存在（26.2 删了）；投掷物接口包是 entity/projectile/throwableitemprojectile。

## 19. 26.2 堆叠上限：getMaxStackSize 在 ItemInstance 接口（不是 ItemStack）

26.2 `ItemStack` 连 `getMaxStackSize` 方法都没有——它在 **`ItemInstance` 接口 default 方法**里（读 `DataComponents.MAX_STACK_SIZE`，默认 1！由 Item 构造时写入组件）。改堆叠上限 mixin 挂 `ItemInstance.class`。**同类教训：先 javap 确认方法宿主，mixin require 才能命中**。

## 20. 告示牌有 4 个方块类

立牌 SignBlock / 墙牌 WallSignBlock / 悬挂 CeilingHangingSignBlock / 悬挂墙牌 WallHangingSignBlock 各自实现 useWithoutItem/useItemOn。mixin 用 `@Mixin({...数组})` 一并覆盖；只挂 SignBlock 时墙牌/悬挂牌不生效。

## 21. 实体碰撞走 getCollisionShape（隐形墙根因）

只覆写 `getShape`（视觉/选择框）**不影响实体碰撞**——碰撞走独立钩子 `getCollisionShape`，默认**整格** → 非完整模型方块（墓碑）四周出现隐形墙。必须同时覆写 `getCollisionShape` 返回贴合形状。

## 22. 26.2 容器默认堆叠上限是 99（不是 64）

`Container.getMaxStackSize()` 默认 **99**（26.2 改过），Slot 放置上限 = `min(container.getMaxStackSize(), itemStack.getMaxStackSize())`。改堆叠上限要同时覆盖：`ItemInstance.getMaxStackSize`（物品侧）+ `Container.getMaxStackSize`（容器侧）。sort/合并逻辑不要写死 64，用 `stack.getMaxStackSize()`。

## 23. 大堆叠踢线根因：ItemStack.CODEC 硬编码 intRange(1,99)

26.2 `ItemStack.MAP_CODEC` 的 count 字段 `ExtraCodecs.intRange(1, 99)`——**validatedStreamCodec 在服务端 decode 时重新用 CODEC 校验**，count>99 直接 DecoderException 踢线（`set_creative_mode_slot` 等）。光改 `getMaxStackSize` 返回值不够。
修法：@Redirect 命中 **`lambda$static$1`**（MAP_CODEC 的 RecordCodecBuilder lambda，javap -c 找 intRange 调用所在合成方法）。
mixin 选择器注意：类初始化写 `<clinit>()V`；**`"static {}"` 会被当正则解析报 Malformed quantifier**；常量若在 lambda 内，必须指名合成方法。

## 24. 视觉工具失效时用行为推断

qwen 视觉配额耗尽/modlens 引擎缺失时，碰撞箱截图看不了——用**用户行走方向线索**（哪边有墙哪边没有）+ 字节码/源码双钩子（getShape vs getCollisionShape）反推根因，比反复猜快。

## 25. 大堆叠语义完整性

放大 `getMaxStackSize` 必须**排除**：`MAX_DAMAGE`（耐久物品）、`STORED_ENCHANTMENTS`/`ENCHANTMENTS`（附魔书/附魔物品）——否则创造栏能一把抓 999 把剑，违背原版"耐久/附魔物品不可堆叠"语义。数字显示配套：`GuiGraphicsExtractor.itemCount` 的 `String.valueOf(count)` redirect → ≥1000 转 k/m 短串。

## 26. 静态初始化 redirect 不得依赖运行时开关

`ItemStack` 等 `<clinit>`/lambda 静态方法在**极早期**执行（模块/配置尚未就绪），redirect 里调 `WlyModule.on(...)` 会拿到 false 并**永久锁定默认行为**。这类 redirect 只能写死放宽值（如 `intRange(1, 9_999_999)`），运行时再靠 getMaxStackSize 等动态钩子收口。

## 27. 物品展示框是实体不是方块

ItemFrame/GlowItemFrame 走 `UseEntityCallback`（不是 UseBlockCallback）；穿透实现 = 实体右键时对视线后方方块手动 useItemOn/useWithoutItem。

## 28. 穿透类功能必须留"正常使用"后门

所有穿透（告示牌/展示框等）统一：**按住 shift（isSecondaryUseActive）= 不穿透，走原版交互**。实现点在服务端入口 handler 最前面判断并 return PASS。

## 29. 分层钳制要"层层兜底"（大堆叠三轮追踪终局）

堆叠上限在 26.2 分三层各自生效：①物品组件 `MAX_STACK_SIZE`（Item 构造写入 64/16/1）②接口 `ItemInstance.getMaxStackSize` default ③`Slot.getMaxStackSize(stack)=min(container, item)`。**mixin 只挂②在"创造拿取"生效、在"放入容器"的调用点不生效（该处虚分派未经过接口 default 的原因不明——javap 无 override 但行为不符）**。终局方案=②之外再挂③（Slot 层兜底 max(返回值, 配置值)）+①的 CODEC 放宽。**教训：涉及 max/min 链的数值功能，每一层都要有 mixin 兜底，别赌单一注入点全覆盖。**

## 30. 大堆叠调试方法论（已沉淀的完整链路）

26.2 堆叠钳制分散在：组件值（Item 构造）→ ItemInstance.getMaxStackSize（接口 default）→ Slot.getMaxStackSize(stack)=min(container,item) → safeInsert → CODEC(1,99)。**诊断顺序**：/bigstacktest 绕开创造拿取 → Slot 层打印组件原值 → 逐层 mixin 兜底（CODEC 放宽、ItemInstance 注入、Slot 层兜底）。**注意**：接口 default @Inject 在部分调用点不生效（原因不明，虚分派路径差异），**必须 Slot 层兜底**；runServer 无玩家无法触发 Slot 路径，必须用户实测+打点回收。

## 31. 大堆叠终局：原型层（getPrototype）才是必中点

多轮追踪后确认：接口 default（ItemInstance.getMaxStackSize）的 @Inject **命中不稳定**（创造拿取命中、Slot 放置路径不命中，同一 JVM 内表现不一）。**必中注入点 = ItemStack.getPrototype()**（具体方法、所有组件读取的源头）：RETURN 时重建 DataComponentMap 并 set(MAX_STACK_SIZE, 配置值)，排除 MAX_DAMAGE/ENCHANTMENTS 物品。组件层一改，Slot/safeInsert/CODEC 全链路的 min(容器, 物品) 自然放大。**选注入点先找"具体实现的方法"（javap 有方法体），接口 default 只当锦上添花。**

## 32. 大堆叠终局（本轮实证）：ENCHANTMENTS 排除条件误伤

`DataComponentHolder.has(ENCHANTMENTS)` 在 26.2 对**未附魔普通物品**也可能返回 true（组件存在性≠"已附魔"）→ 排除条件误伤全部物品 → 大堆叠失效。**正确条件：只排除 MAX_DAMAGE**（工具/武器/盔甲不可堆），附魔书与普通物品可堆。另：接口 default @Inject 必须 **require=1**——之前"静默无效"实为注入点没命中，require=1 让它暴露并被修复（命中后反射实测 999）。

## 33. 生成类 doFill 是 返ChunkAccess 的方法（注入需 CallbackInfoReturnable）

`NoiseBasedChunkGenerator.doFill` 返回 `ChunkAccess`——`@Inject` 到**有返回值**的方法必须用 `CallbackInfoReturnable<T>`（用 `CallbackInfo` 会 InvalidInjectionException）。注入前先 javap 确认目标方法签名（返回类型决定 Callback 类型）。另：跨维度判断用 `getMinY()==-64` 作为主世界代理（ChunkAccess 无 getLevel）；`StructureManager` 包是 `net.minecraft.world.level`（不是 `.levelgen.structure`）。

## 34. 世界生成期异步线程内写方块 = 死锁高危

`NoiseBasedChunkGenerator.doFill` 在**异步生成线程**执行——在其中调用 `ChunkAccess.setBlockState`（尤其"强制放基岩"）会与正在填充的 chunk 锁回环 → **新世界生成卡死**（用户实测强制关才退）。
**规则**：生成期钩子只读不写；必须写方块的事件要放到**区块已生成完成**后再做（chunk load / server tick 扫描），切勿在 fillFromNoise/doFill 内 setBlockState。涉及高风险的生成类功能默认关闭（enabledByDefault=false），由用户手动开启并小心测试。

## 35. 生成类功能：务必用 CHUNK_GENERATE 而非 doFill 写方块

平滑基岩终局方案：**`ServerChunkEvents.CHUNK_GENERATE`**（区块生成完成后的安全时机，LevelChunk 已落地）里压平基岩；之前 mixin `NoiseBasedChunkGenerator.doFill`（异步生成线程写方块）导致**新世界生成卡死**。口诀：**生成期钩子只读；写方块放到 CHUNK_GENERATE / chunk load / tick 扫描**。跨维度判断仍用 `level.getMinY()==-64`（LevelHeightAccessor.getMinY，不是 getMinBuildHeight）。

## 36. 性能铁律：mixin/事件回调里禁止高频日志

`Slot.getMaxStackSize(ItemStack)`、`Container.getMaxStackSize()` 等是**容器每次交互都会调用**的热点方法，
在里面打 `LOGGER.info`（字符串格式化+IO）会直接拖慢背包/箱子操作。**调试打点用完必删**，
只保留一次性事件（注册完成/死亡等）的日志。高频周期重复计算的网络同步（如按键状态）也要降频：
变化即时发 + 稳定保持仅心跳（100 tick），不能每 5 tick 重发。

## 37. 大堆叠排除条件已统一（slot 层不再检查 ENCHANTMENTS）

`has(DataComponents.ENCHANTMENTS)` 会误伤正常物品（存在性检查 ≠ “已附魔”），
三层（ItemInstance/Slot/Container）统一为**只看 MAX_DAMAGE** 排除耐久工具；附魔书与普通物品可堆。

## 38. 联动配置项：Cloth 分组循环内按 id 追加子项

给"力量射击"这类带数值/子开关的功能做配置时，不用单开分类——在 WlyConfig 的**模块开关循环内**按 `id.equals("powershot")` 就地追加 3 个条目（初速倍率/伤害开关/伤害上限），保证它们在 GUI 里紧邻开关下方（联动项同组相邻）。
持久化：WlyConfigData 的 load/remove/save 三处各加对应键（__powerVelocity/__damageEnabled/__damageMax），与既有 __eatFullCap 模式一致。

## 39. 26.2 投掷物伤害注入点 = ThrowableProjectile.onHitEntity

雪球/珍珠/鸡蛋等 ThrowableProjectile 命中实体的钩子是 `protected onHitEntity(EntityHitResult)`（TAIL 注入）；
伤害源用 `target.damageSources().thrown(this, getOwner())`；该钩子在服务器端执行，安全。

## 40. 方法声明在基类：@Mixin 目标必须指向声明类，不能指向中间子类

`ThrowableProjectile` 不声明 `onHitEntity`（在父类 `Projectile`）。若 @Mixin(ThrowableProjectile) 注入 method="onHitEntity"，会直接注入失败/注入到父类（实测 NoSuchMethodException 反射证实）。
教训：注入继承方法时，先 javap 确认**方法声明在哪一层**，@Mixin 就指向那一层；子类（雪球/鸡蛋/珍珠）覆写并调 super 即可触发注入。

## 41. 26.2 实体注册：EntityType 静态常量已拆，实体取用走 BuiltInRegistries

`EntityType.ZOMBIE` 等常量 26.2 已不存在（`javap EntityType` 无 ZOMBIE），统一走 `BuiltInRegistries.ENTITY_TYPE.get(Identifier).map(Holder.Reference::value)` 取 `EntityType<?>`（注意返回 Optional），create 用 `EntitySpawnReason.MOB_SUMMONED`。

**两版对照（写跨版本代码时必须知道）**：

| 版本 | 常量挂在哪 | 取 `SnowGolem` 类型 |
|---|---|---|
| 26.1.2 | `net.minecraft.world.entity.EntityType`（该类**同时**是类型和常量表） | `EntityType.SNOW_GOLEM` |
| 26.2 | `net.minecraft.world.entity.EntityTypes`（新建的常量表类） | `EntityTypes.SNOW_GOLEM` |

26.2 的 `EntityType` 只剩类型本身（javap 55 行，无任何实体常量）。两版**类名不同** → 无法用同一符号编译，

```java

    @Override   // ← 缺 }，displayName 未闭合 = 语法错误
```

症状：`gradlew build` 编译全灭 / IDE 红浪一片；git diff 却只显示"return 那行变了"，极难发现。
排查：`rg 'return "wly\.module\." \+ ID;$' src/main/java -l | wc -l` 与模块总数对不上；或 grep 方法体后是否紧跟 `    }`。

## 46. i18n 语言键陷阱（显示/英文失效）

1. **en_us 键前缀必须与代码生成规则一致**：`displayName()` 返回 `wly.module.<id>`，en_us 就必须是 `"wly.module.<id>"`。曾误写成 `module.<id>`，英文客户端所有模块名变成裸键。
2. **`Component.literal()` 不解析翻译键**：`Component.literal(m.displayName())` 显示的是键名本身（`wly.module.powershot`），不是翻译文本。GUI 一律用 `Component.translatable(key)`；消息用 `translatable(key, args...)` + 公共前缀拼接，颜色用 `.withStyle(ChatFormatting.XXX)` 而不是往语言字符串里塞 `§` 码。
3. **语言文件键集必须双侧对齐**：新增语言键要同时进 `zh_cn.json` 与 `en_us.json`；SelfTest T10 已加 en_us 键集校验（含 eztweak 子规则键），改语言文件后跑自检。
4. **`%1$s` 位置参数在语言字符串中可用**（`%%` 表示字面 `%`），传参 `Component.translatable(key, arg1, arg2)`；Component 也可作参数（会嵌套渲染）。

## 47. 双版本兼容（26.1.2 / 26.2）：运行期只有 2 个 API 分叉点（症状标签：致命/失效）

**症状**：26.2 上正常的 jar 装到 26.1.2 → `NoSuchMethodError: net.minecraft.client.gui.Gui.screen()`；
或启动期崩在墓碑方块实体注册（`BlockEntityType` 构造器 private 访问控制）。

**根因**：两版 jar 的类清单差 570/300 个类，但**本项目实际用到的运行期 API 只有两处分叉**：

1. 「当前屏幕」：26.2 走 `Gui.screen()` 方法；26.1.2 是 `Minecraft.screen` 公有字段（26.2 已删掉该字段）。
2. `BlockEntityType(BlockEntitySupplier, Set<Block>)` 构造器：26.1.2 是 **private**，26.2 才放开为 public。

**另有 1 处「编译期分叉」（不影响产物，只在写代码时会踩）**：实体类型常量在 26.1.2 挂在
`EntityType.SNOW_GOLEM`，26.2 整体搬到 `EntityTypes.SNOW_GOLEM`（详见 #41）。
因为发布源码**不引用任何实体常量**，产物不受影响；只有自检/调试代码需要时，用反射兜底（见 `SelfTest.snowGolemType()`）。

其余 mixin 目标**两版声明完全一致**（用 `tools/injection_audit.py` 对两版 jar 逐个 javap 核对，56 个目标全过）；
关键注入点签名（`ItemInstance.getMaxStackSize`、`ItemStack.lambda$static$1`、`Projectile.onHitEntity`、
`FoodData.add`、`LivingEntity.handleOnClimbable`、`Projectile.spawnProjectileFromRotation`）也逐个人工比对一致。

**规则**：

- 构建基线钉在 **26.1.2（兼容下限）**，编译器强制只用两版都存在的 API；26.2 开发环境加 `-Pmc=26.2`。
  实测两版产物**除 `MANIFEST.MF` 里 `Fabric-Minecraft-Version` 一行外，全部条目字节一致**
  （jar 内无 refmap —— Loom 构建期直接把 mixin 引用 remap 到 intermediary，天然跨版本）。
- 取当前屏幕一律走 `com.minecraftloveyou.client.ClientCompat.currentScreen()`（反射双路兜底）。
- 注册方块实体类型一律走 `FabricBlockEntityTypeBuilder.create(...).build()`，别用裸构造器。
- 新增/改动 mixin 后跑 `python tools/mixin_audit.py`：目标类缺失 = 另一版必崩；
  成员只在单边声明 = 另一版**静默失效**（`defaultRequire=0` 不报错，最难查）。
- `fabric.mod.json` 的 `java` 要写 `>=25`（两版都是 Java 25 运行时，写 `>=21` 只会给出误导性报错）。

## 48. 注入目标不能是 abstract 方法（症状标签：失效）

**症状**：模块开关能开能关，但游戏里毫无效果，日志里没有任何报错。
**根因**：`KeyBindsListMixin` 把 `@Redirect` 挂在 `KeyBindsList$Entry.refreshEntry`，而该方法是 **abstract**（无字节码）；
真正实现在子类 `KeyBindsList$KeyEntry.refreshEntry`（只有那里才有 `KeyMapping.same(...)` 调用）。
mixin 只改写 target 类自身的方法体，抽象方法没有方法体 → 注入点找不到 → `defaultRequire=0` 静默跳过。
（26.1.2 / 26.2 两版都是这个结构，所以「全键无冲」在 26.2 上也一直没生效。）
**规则**：

- `@Mixin(X.class)` 的 `method` 必须指向**有方法体**的声明；先 `javap -p` 看那一行有没有 `abstract`。
- 遇到 abstract 声明，改挂**实现该方法的子类**（本例 `KeyBindsList$KeyEntry`，public 内部类可直接 `.class`）。
- **继承 ≠ 无效**：子类不覆写、实现在父类，且父类也是本 mixin 的 target 时，虚分派仍会走到被注入的父类实现
  （如 `ClickthroughSignMixin` 挂 `SignBlock` 就覆盖了 `WallSignBlock`）——这种情况**是生效的**，别误改。
- 交付前跑 `python tools/injection_audit.py --mc both`：逐项核对「方法是否声明 / 是否 abstract /
  `@At` 指向的成员是否真在该方法字节码里 / `ordinal` 是否越界」，并区分 require=0 的**静默失效**与 require>=1 的**崩溃**。

## 49. 别把「编译通过 + runServer 绿」当成功能可用

**症状**：连续多次出现「改了但用户说没效果」。
**根因**：`minecraft_love_you.mixins.json` 设了 `"injectors": { "defaultRequire": 0 }`——
任何没显式写 `require` 的注入器失败时**不报错也不崩**，只是那个功能永远不生效。
**规则**：改完 mixin 必跑 `python tools/injection_audit.py --mc both`（静态可达性）+ `python tools/mixin_audit.py`（跨版本一致性），
再按 AGENTS.md 的验证清单走一遍「触发路径是否真实可达」。

## 51. 「去实验设置警告」失效：注入点选错 + defaultRequire=0 静默跳过（症状标签：失效）

**症状**：`no-exp-warn` 开着，进实验性 / 自定义世界照样弹警告屏，日志里没有任何报错。

**根因**：26.x 把「劝告」逻辑从 `CreateWorldScreen` 挪到了 `WorldOpenFlows` 的三条路径上。
原 mixin（`NoExpWarnMixin`）只把 `CreateWorldScreen.tryApplyNewDataPacks` 里的
`FeatureFlags.isExperimental` 重定向为 false —— 那只管**创建**世界侧，管不到**进入已有世界**。

**正解（三道闸，26.1.2 / 26.2 字节码一致，已 javap 核对）**：

1. `WorldOpenFlows.askForBackup(access, customized, onProceed, onCancel)` —— 真正的备份劝告屏。
   `@Inject(at = HEAD, cancellable = true)`，执行第 3 参 `onProceed`（等价玩家点「继续」）后 cancel。
2. `WorldOpenFlows.openWorldCheckWorldStemCompatibility` —— 把
   `WorldData.worldGenSettingsLifecycle()` `@Redirect` 成 `Lifecycle.stable()`，从源头掐掉实验性判定。
3. `WorldOpenFlows.confirmWorldCreation(mc, screen, lifecycle, onProceed, bl)` 是**静态**方法，
   `bl` 落在 slot 4；`@ModifyVariable(argsOnly = true, index = 4, require = 1)` 强制 true。

**破译参考模组的方法**：不要只看类名——`DisableCustomWorldsAdvice` 的 refmap 里写 `class_7196`，
初看像 `IntegratedServerLoader`，实际是 `WorldOpenFlows`。要用 refmap 的 `method_57775` / `method_41892`
反查真实方法名，再 `javap -c` 核对参数槽位。

**教训**：本项目 `mixins.json` 是 `defaultRequire: 0` —— 注入点找不到时**静默跳过、不报错**。
凡「开关能开但游戏里没效果」，先假设注入点根本没挂上，用 `tools/injection_audit.py` + `javap` 核对，
必要时对关键注入显式加 `require = 1`，让它在启动期变响。

## 52. 「只对玩家阵营生效」的作用域口径必须单点定义（症状标签：漏判）

**背景**：力量射击（`powershot`）与移除受击无敌帧（`rendi`）都要求「只作用于玩家本人 + 玩家的宠物」。

**坑**：原先 powershot 的过滤器写的是
`e instanceof Player || (e instanceof OwnableEntity o && o.getRootOwner() instanceof Player)`，
**漏了雪傀儡** —— `SnowGolem` 既不实现 `OwnableEntity`、也没有 owner 字段（只能由玩家建造、无自然生成），
于是「雪傀儡扔出的雪球不吃速度加成」。同理 rendi 直接对**所有** `LivingEntity` 清零无敌帧，
玩家自己和宠物也被连击秒杀。

**正解**：口径抽到 `com.minecraftloveyou.core.PlayerSide.isPlayerOrPet(Entity)` 单点定义，两处共用：

1. `Player` → 是；
2. `SnowGolem` → 是（按**类型**整体归属，因为它只能由玩家建造且无 owner 字段）；
3. `OwnableEntity` 且 `getRootOwner() instanceof Player` → 是（`getRootOwner` 沿 owner 链回溯，覆盖「宠物的宠物」）；
4. 其余 → 否。**铁傀儡不算**（会自然生成于村庄，不能整体算玩家的）。

**教训**：多个功能共用一个「作用域」概念时，判定必须单点定义（放 `core/`），不要在两处各写一份 ——
口径漂移的表现就是「A 功能生效了、B 功能漏判」。

## 53. 在 CHUNK_LOAD 回调里写方块 = 卡在加载地形（症状标签：死锁/卡死）

**症状**：进世界后**永久卡在「加载地形中」**，日志最后一行停在
`准备生成区域中：37%`（37% 正是 `Loading 49 chunks for player spawn` 那一步），
之后一小时都没有新日志，游戏窗口无响应，但**没有任何异常/崩溃报告**。

**根因**：`offline-catchup` 在 `ServerChunkEvents.CHUNK_LOAD` 回调里直接做补偿，
而补偿会写方块：
- `AbstractFurnaceBlockEntity.serverTick(...)` 内部会执行
  `ServerLevel.setBlock(pos, state, 3)`（javap 确认 `iconst_3` → flag 3 = 更新邻居 + 同步客户端）；
- `CropBlock.growCrops(...)` 内部 `level.setBlock(pos, state, 2)`。

flag 含 `UPDATE_NEIGHBORS` → `Level.updateNeighborsAt` → 读相邻方块 →
`Level.getBlockState(neighbor)` → 邻居区块若尚未加载 → `ServerChunkCache.getChunk(x,z,FULL,true)`
→ **`.join()`** —— 而此时正是同一个线程在 `prepareLevels` 里装载区块，
future 永远等不到 → **重入死锁**。

**规则**：

- **`CHUNK_LOAD` / `CHUNK_UNLOAD` / `ENTITY_LOAD` 回调里只允许记录/入队，不得读写世界。**
  真正的世界操作搬到 `ServerTickEvents.END_SERVER_TICK`，用
  `level.getChunkSource().getChunkNow(x, z)` 取回区块（返回 null 就跳过）后再执行。
- 每次处理都要有时间预算（本项目 8ms/tick）与条数上限，避免一次性灌入数万区块时拖垮服务器。
- 需要写方块的功能（补种、催熟、铺雪、刷怪笼……）一律按这个模式写。

**定位方法**：卡住时看日志最后一行落在哪个阶段；再用 `git` 对比「上一次正常会话」与
「卡死会话」之间**新增了哪个模块**（本例 12:25 会话正常、13:59 会话卡死，中间只多了
`offline-catchup` 一个模块）。

## 54. 离线追赶（offline-catchup）v2 设计要点

对齐 Unloaded Activity 后确定下来的几条：

1. **延迟执行**：见 #53。`CHUNK_LOAD` 只入队 `(level, cx, cz, deltaMs)`，不持区块引用。
2. **通用随机刻**：不要逐个方块写生长规则，直接按原版随机刻模型折算期望次数，
   再调用原版 `BlockState.randomTick`：
   每 tick 每个 16³ 段从 4096 个位置里选 `randomTickSpeed` 个 →
   某方块在 `ticks` 刻内被选中的期望次数 = `ticks × randomTickSpeed / 4096`。
   作物、树苗、草、藤蔓、茎、雪、冰全部自动覆盖，且行为与原版一致。
   单方块上限**分两档**：生长档 256 次、其它档 16 次（见 #55 第 2 条，7 天离线也不会跑出天文数字）。
3. **停机时间戳必须有窗口**：`stopStamp` 只在「服务器启动后的补偿窗口」内有效
   （本项目 600 tick，队列没排空则最多 1800 tick）。否则玩家本次游玩中新加载的
   远处区块会全部按「停机至今」重复补偿 —— 越玩越卡。
4. **不要在 `CHUNK_LOAD` 里 `touch()`**：同一区块的实体是在 `CHUNK_LOAD` 之后
   立刻触发的 `ENTITY_LOAD`；若 `CHUNK_LOAD` 先把时间戳刷成「现在」，
   实体侧算出的 delta 恒为 0，**动物年龄补偿会永远失效**。
   时间戳改为在 `END_SERVER_TICK` 消费完队列后再刷新。
5. **没有时间基准就不补偿**：`lastActive` 返回 0（本会话首次遇到且没有停机戳）时直接跳过，
   不要把 0 当成「1970 年」算出天文数字 delta。
6. `AgeableMob.ageUp(ticks, false)` 只改实体状态、不写方块，但为了口径统一也一并延迟处理，
   并在处理时重新校验 `isRemoved()/isAlive()`。


## 55. 只在 SERVER_STOPPING 写时间戳 = 强杀后「离线追赶完全无效」（症状标签：功能无效）

**症状**：离线追赶看起来在跑（日志有补偿行），但用户实测「**完全没效果**」：
关掉游戏一段时间再进来，熔炉没烧完、作物没长、动物没长大。

**根因（两层，第一层是主因）**：

1. **时间基准丢失**：v2 只在 `ServerEvents.SERVER_STOPPING` 时把停机时间戳写入
   `wly_offline_catchup.txt`。而玩家**强杀进程 / 游戏崩溃**时该回调不会触发
   （本项目最常见：卡在加载地形被强杀、OOM、直接关窗口）。
   于是下一次启动 `stopStamp == 0` → `lastActive()` 返回 0 → `deltaOf()` 返回 0 →
   **一个区块都不补偿**。

   **判定方法**：日志里若**没有**`[世界爱你] 离线追赶：启动补偿窗口结束...`这一行，
   就说明这次启动 `stopStamp == 0`（该行只在 `stopStamp != 0` 时才打印）。

   **修法**：加**心跳**。服务器运行期间每 15 秒把 `System.currentTimeMillis()`
   写入同一个文件（`END_SERVER_TICK` 里按墙钟节流，不按 tick 数，避免 TPS 波动影响），
   停机时再写一次精确值。强杀最多只丢 15 秒的离线时间。
   顺带做时钟回拨保护：读到的时间戳 > now + 60s 时按 0 处理。

2. **作物档上限太小**：通用随机刻的单方块上限统一是 16 次。小麦每升一级平均需要
   **26 次**随机刻，长熟约需 **180+ 次**；离线 8 小时的期望值 ≈ 421 次，
   被 16 一刀切掉 → 作物几乎不动，看起来「没效果」。
   16 这个数是为了防「草方块蔓延/雪/冰」这类**海量**方块拖垮区块加载，
   不该套在生长方块上。

   **修法**：随机刻分两档 ——
   - **生长档**（`age` / `stage` / `age_N` 属性的方块，含模组作物）：上限 **256**；
   - **其它档**（草蔓延、雪、冰、树叶衰减等）：仍为 **16**。

   用**属性名**判定而不是用类判定，才能同时覆盖原版作物与模组作物
   （例如植物大战僵尸的植物）。
   **必须排除 `BaseFireBlock`**：火也有 `age` 属性，按离线时间补 256 次随机刻
   会把整片森林烧干净。

**规则**：任何「按现实时间补偿」的功能，时间基准都必须能容忍**非正常退出**——
心跳/定期落盘，不能只依赖优雅停机回调。

## 56. `AgeableMob.ageUp(int, boolean)` 的参数是**秒**不是 tick

javap 26.1.2 确认：

```
ageUp(int, boolean):
  age += arg0 * 20;     // ← 乘 20
  if (age > 0) age = 0; // 成年后封顶
```

所以 `mob.ageUp(ticks)` 会把进度放大 20 倍：离线 **1 分钟**（1200 tick）传进去
→ `age += 24000` → 幼年动物**直接成年**。

正确写法：`mob.ageUp((int)(deltaMs / 1000L), false)`，即参数 = 离线**秒数**。


## 57. `fabric.mod.json` 的 `depends` 里写客户端模组 = **专服直接起不来**

`cloth-config` / `modmenu` 都是 `environment: client` 的模组。专服上 Fabric **不会加载**它们，
于是 `depends` 解析失败 → `ModResolutionException`，服务器根本进不到主菜单。

**规则**：只把「真正运行时必需且两端都存在」的写进 `depends`。
配置界面/Mod Menu 这类纯客户端便利依赖，一律写 `recommends`（缺失只告警）。
`environment` 保持 `*`（本模组有 `main` 与 `client` 两个入口点）。

## 58. Gradle `processResources` 的 `expand` 会把 `
` 吃成真换行

`fabric.mod.json` 里写 `"description": "...。
English..."`，
经过 `filesMatching("fabric.mod.json") { expand "version": ... }` 之后，
jar 内文件里那段是**真的 0x0A 字节**，而不是转义序列 `
` → 严格 JSON 解析器会报
`Invalid control character`。

Fabric Loader 用的是宽松 Gson，所以**能跑**，但这是个定时炸弹。
**修法**：源文件里写双反斜杠 `\n`，让 Groovy 处理后正好剩一个 `
`。
**校验**：`python -c "import zipfile,json; json.loads(zipfile.ZipFile('build/libs/xxx.jar').read('fabric.mod.json'))"`
能过才算干净。

## 59. 26.x 没有 `CommandSourceStack.hasPermission(int)`

26.x 换成了权限对象模型：

```
CommandSourceStack.permissions() -> PermissionSet
PermissionSet.hasPermission(Permission)
net.minecraft.server.permissions.Permissions.COMMANDS_MODERATOR / GAMEMASTER / ADMIN / OWNER
```

原版 `hasPermission(2)` 的等价写法：

```java
.requires(src -> src.permissions().hasPermission(
        net.minecraft.server.permissions.Permissions.COMMANDS_GAMEMASTER))
```

（两版都有 `Permissions` 类；`Commands.LEVEL_*` 常量是另一套 `PermissionCheck`，别混用。）

## 60. `destroyBlock(pos, false)` 会**连容器内容物一起抹掉**

`Level.destroyBlock(pos, drop=false)` 只跳过「方块本体掉落」，方块实体仍会被直接移除。
用它把箱子换成别的方块 → **箱子里的东西凭空消失**。

**修法**：替换前先把内容物倒出来：

```java
var be = level.getBlockEntity(pos);
if (be instanceof net.minecraft.world.Container c) {
    net.minecraft.world.Containers.dropContents(level, pos, c);
}
level.destroyBlock(pos, false);
```

**规则**：任何「替换/移除已有方块」的代码，都要先问一句：这块可能是容器吗？

## 61. 同一个物理量在两处各放大一次 = 双重放大

攀爬功能曾在两个地方各乘一次速度：
- `LivingEntityClimbMixin` 把 `handleOnClimbable` 的下行下限 `-0.15` 放大成 `-0.15 * speed`；
- `ClimbingModule.applyClimbBoost`（`Player.aiStep` TAIL）又把 `d.y < 0` 的分量乘一遍。

`speed=5` 时下行速度到 **-2.55**，直接穿地板。

**规则**：一个物理量只在一处放大。放大点要么全在 mixin 里，要么全在 tick 回调里，
并且**在注释里写明另一个地方不要再乘**。

## 62. 状态包要「状态一变就发」，别把心跳节流套在状态变化上

```java
// 错：tick % 100 == 0 那一 tick 恰好松键时，(held || !resend) 为 false → 松键包被丢
if (client.getConnection() != null && (held || !resend)) send(held);
```

丢一个「松键」包的后果是服务端**永远以为还按着**（连锁键卡住）。
正确写法：状态变化无条件发；心跳重发只用于「保持按住」的幂等补发。

## 63. 开关关了但还在跑 = 静默耗性能（也是「功能无效」的镜像症状）

`minecraft_love_you.mixins.json` 的 `injectors.defaultRequire = 0` 意味着注入失败是**静默**的；
反过来，注入了但**没做 `WlyModule.on("模块id")` 门控**，就是开关关了照样跑。

本项目实际踩到的：
- `EnchantmentMenuSlotsMixin`：关了 `enchant-reveal` 仍在算 3 次 `getEnchantmentList` 并 S2C 发包；
- `ChainKeySender`：关了 `harvest` 仍每 100 tick 心跳发包。

**规则**：每个 mixin 注入方法 / 每个事件回调的**第一行**必须是 `WlyModule.on(...)` 门控
（或 `if (!on()) return;`），无一例外。

## 64. `AttributeInstance.addPermanentModifier` 会写进玩家存档

永久修饰符进 NBT。用它做「重进存档补回装备生命上限」→ 脱掉装备后加成**还在**（属性残留），
而且下次进入又 `addPermanentModifier` 同一个 id 会抛
`IllegalArgumentException: Modifier is already applied`。

**修法**：只在「原版确实没应用」时补差额，且用 `addTransientModifier`（不进存档）；
血量只做「不超过新上限」的收口，**绝不在 JOIN 时补血**——那等于每次重进白送一次满血。


## 65. `@At` 的 `ordinal` 写错也能过审计 —— 只能靠 javap 看上下文

`tools/injection_audit.py` 只能验证「ordinal 没越界」，验证不了「指对了那一处」。

真实案例：`AnvilMenuMixin` 想跳过「待改造物品堆叠时费用钉死 40」，写了
`ItemStack.getCount()` 的 `ordinal = 0`。javap `createResult` 后真相是：

| ordinal | 字节码位置 | 语义 |
|---|---|---|
| 0 | offset 232 | `while (i2 > 0 && j2 < itemstack1.getCount())` —— **用材料修耐久的循环上界**，同时决定 `repairItemCountCost`（吃几个材料） |
| 1 | offset 713 | `if (itemstack.getCount() > 1) cost = 40;` —— 这才是要跳的钳制 |

写错 ordinal 的后果是**静默的功能回归**：铁砧用材料修复变成「只吃 1 个材料、只修 1/4 耐久」。

**规则**：凡是用 `ordinal` 定位的注入点，改完必须 `javap -c` 把**同一方法内所有**匹配调用
按出现顺序列出来，逐个确认语义，并把结论写进注释（像上面那张表）。

## 66. mixin 在「会被反复调用的方法」尾部追加内容 = 越堆越多

`visible-traders` 在 `Villager.updateTrades` 的 TAIL 追加「当前档以上」的假交易。
但 vanilla 在村民**每次升级**（`increaseMerchantCareer`）都会再调一次 `updateTrades`
（javap 确认），于是每升一级就把 3/4/5 档再追加一遍 → 同一档出现 N 份。

**修法**：用 `@Unique` 字段记住上一轮注入的对象（按引用），下次注入前先摘掉：

```java
@Unique private List<MerchantOffer> wly$injected = new ArrayList<>();
// TAIL 开头：
if (!wly$injected.isEmpty()) { offers.removeAll(wly$injected); wly$injected.clear(); }
```

`MerchantOffer` 没重写 `equals` → `removeAll` 按引用比较，不会误删 vanilla 自己加的交易。
**不要**用「记住 size 然后从尾部截断」——vanilla 可能在你注入之后又追加，会把它的真交易删掉。

**规则**：往一个**可重复调用**的方法尾部追加状态时，先问一句「这个方法会被调用几次」。

## 67. 创造模式不消耗物品的判定要**逐条**加

`HarvestModule` 的种植分支有 `if (!player.getAbilities().instabuild) seed.shrink(1)`，
但补种分支 `consumeSeed()` 漏了 → 创造模式收一次作物就少一颗种子。
`BeaconFillModule` 的 `held.shrink(1)` 同样漏了。

**规则**：任何 `shrink()` / 消耗物品的地方，都要单独问一句「创造模式该不该扣」，
不能因为「旁边那条路径判过了」就默认这条也判过。

## 68. 「离线追赶」的触发点只挂在 CHUNK_LOAD 上 = 一半场景零补偿

**症状**：玩家报「离线追赶原地睡醒以后仍无效」。日志里 152 分钟的离线补偿明明成功了
（`补偿 682 个区块 / 99 只动物……`），但之后一路 `补偿 0 个区块`。

**根因**：把「时间流逝」等价成了「区块重新加载」。实际上「现实时间在流逝、但世界没推进」
有**四种**互不相同的成因，`CHUNK_LOAD` 只覆盖前两种：

| 成因 | 现实时间在流逝吗 | 世界在 tick 吗 | `CHUNK_LOAD` 会触发吗 |
|---|---|---|---|
| 退出游戏 / 强杀后重进 | ✅ | ❌ | ✅（`Loading N persistent chunks`） |
| 跑远导致区块卸载后再回来 | ✅ | ❌（该区块） | ✅ |
| **暂停 / 窗口失焦自动暂停 / 电脑睡眠休眠** | ✅ | ❌ | **❌ 区块从未卸载** |
| **用床跳过夜晚** | ✅ | ✅（但那段世界时钟被抹掉） | **❌** |

后两种情况下 `CHUNK_QUEUE` 恒为空 → 零补偿。玩家看到的就是「功能时灵时不灵」。

**修法**：在 `END_SERVER_TICK` 里补两条独立通路，都只是「入队」，
真正干活仍然走 `drainChunks` / `drainEntities`（保持「回调里只入队、不碰世界」这条铁律）：

1. **世界停摆**：记住上一次 tick 的 `System.currentTimeMillis()`，
   本次差值 ≥ 10s 就判定为世界被冻结 → 把玩家周围 10 区块内**已加载**的区块与动物按该差值入队。
   关键点：`onEndServerTick` 在**模块关闭时也要更新这个基准**，否则中途打开模块会把
   已经流逝的现实时间当成一次停摆，一次性巨量补偿。
2. **睡觉跳过夜晚**：26.x 起 `Level` 没有 `getDayTime()` 了（改成世界时钟体系），
   用 `Level.getOverworldClockTime()`（= 世界时钟总刻数，正常每 tick +1）。
   单 tick 前跳落在 `[100, 24000]` 刻即认定为跳过夜晚，按 `跳变刻数 × 50ms` 补偿。

**两个必须加的护栏**：

- 停摆差值要设上限（这里 12 小时），防系统时钟跳变。
- 睡觉判定要加**冷却**（这里 200 tick）。因为时钟倍速类模组会让世界时钟每 tick 前跳上百刻，
  没有冷却就会每 tick 灌满队列。加冷却后最坏情况每 10 秒补 100 刻
  （折算随机刻期望 ≈ 0.07 次/方块 → 实际零生长），完全无害。

**排查入口**：两条通路各自打一行独立日志
（`检测到世界停摆 X（暂停 / 窗口失焦 / 系统休眠 / 长时间卡顿）`、
`检测到睡觉跳过夜晚 X`），用户报「仍无效」时先看这两行有没有出现，
就能立刻区分「没触发」还是「触发了但没效果」。

**规则**：给「时间补偿」类功能定触发点时，先穷举「现实时间流逝」的全部成因，
再逐个问「这个成因下我的触发点会不会响」。只挂一个事件回调 = 静默漏掉一半场景。

## 69. `@At target` 的方法描述符**必须**写括号形式（症状标签：致命/启动崩）

**症状**：`WLY_SELFTEST=1 runServer` 启动期直接崩，栈顶是
`InvalidMemberDescriptorException: Invalid name: onEnchantmentPerformed:`（名字尾巴上多一个冒号）。

**根因**：`MemberInfo.parse` 的解析顺序是「**先找 `(`，再找 `:`**」：

```java
int parenPos = ref.indexOf('(');   // ← 先判这个
int colonPos = ref.indexOf(':');
if (parenPos > -1) { desc = ref.substring(parenPos); ref = ref.substring(0, parenPos); }
else if (colonPos > -1) { desc = ref.substring(colonPos + 1); ref = ref.substring(0, colonPos); }
// 之后才剥 owner：lastIndexOf('.') 优先，否则 `L...;` 前缀
```

所以**方法**写成冒号形式 `Lowner;name:(args)ret` 时，`(` 先被命中 →
`name` 变成 `name:`（冒号被粘进名字）→ 校验失败，**加载期硬崩**。

| 写法 | 适用 | 结果 |
|---|---|---|
| `Lnet/.../Player;hasInfiniteMaterials()Z` | 方法 ✅ | OK |
| `Lnet/.../Player;getUseDuration(Lnet/...;I)I` | 方法（desc 含 `;`）✅ | OK |
| `Lnet/.../Player;experienceLevel:I` | **字段** ✅ | OK |
| `Lnet/.../Level$ExplosionInteraction;MOB:L...;` | **枚举常量** ✅ | OK |
| `Lnet/.../Player;giveExperienceLevels:(I)V` | 方法 ❌ | **启动崩** |
| `Lnet/.../Player;onEnchantmentPerformed:(Lnet/...;I)V` | 方法 ❌ | **启动崩** |

**规则**：`@At target` 里凡是**方法**，一律写 `name(args)ret`；冒号形式只留给字段/枚举常量。

**已补护栏**：`tools/injection_audit.py` 新增 `malformed_target()`，用 Python 镜像上面这段
解析逻辑，凡是解析出的成员名不是合法 Java 标识符就报 **HIGH**。
（旧版脚本的 `norm_member()` 会把 `name:(` 归一化成 `name(`，**恰好把这个 bug 洗掉**，
所以 63 项全 OK 却仍然启动崩 —— 归一化不能替代语法校验。）

## 70. `Player.totalExperience` 是「累计获得」不是「当前可花」，不能当货币

想给「按经验值结算」找个字段时，很容易顺手用 `player.totalExperience`。**错的**：
javap 确认 `giveExperienceLevels(-n)` **不会**减 `totalExperience`，它只增不减，
是「这局累计获得过多少经验」的统计量。拿它当钱包 → 花掉的经验永远扣不掉。

**正确做法**：从 `experienceLevel` + `experienceProgress` 现算，O(1) 分段求和
（`XpPointsModule.of(Player)`）：

| 等级区间 | 升到下一级需要的点数 |
|---|---|
| 0 ~ 14 | `7 + 2·level` |
| 15 ~ 29 | `37 + 5·(level − 15)` |
| 30 + | `112 + 9·(level − 30)` |

锚点：0 级 = 0 点，**15 级 = 315 点**，**30 级 = 1395 点**（自检 T15 已断言这三个值）。
最后再加上 `experienceProgress × getXpNeededForNextLevel()` 的当前进度部分。
扣费走 `giveExperiencePoints(-n)`（它自己会处理「进度扣成负数就掉级」）。

## 71. 服务端放行 ≠ 客户端「过于昂贵！」文案放行（症状标签：失效）

铁砧的「过于昂贵」是**两处独立**的实现，只改一处 = 玩家仍然看到红字：

1. **服务端** `AnvilMenu.mayPickup` / `onTake` —— 决定**能不能取件**、扣多少级。
2. **客户端** `AnvilScreen.extractLabels` —— 决定**显示什么文案**：
   `cost >= 40 && !player.hasInfiniteMaterials()` → 显示 `TOO_EXPENSIVE_TEXT`。

只注入服务端，玩家看到的是「红字『过于昂贵！』但能取件」—— 反而更像 bug。

**注意客户端那处的 owner 是 `LocalPlayer` 而不是 `Player`**（javap：`invokevirtual LocalPlayer.hasInfiniteMaterials:()Z`），
服务端 `mayPickup` 里才是 `Player.hasInfiniteMaterials:()Z`。两处 target 不能互相抄。

**规则**：改任何「界面上的限制/提示」前，先分别 `javap` **服务端菜单类**和**客户端 Screen 类**，
确认同一个限制是不是被写了两遍。

## 72. 改 mixin 后**必须**跑一遍 `runServer` 才能算验证过（症状标签：致命/启动崩）

`injection_audit.py` 是**静态**审计：它只看「目标成员在不在字节码里」「ordinal 越不越界」，
**看不到** Mixin 注解本身的解析期错误（#69 那种）、也看不到 `require` 之外的运行期绑定失败。

**v1.2.4 实锤**：审计脚本报 `63 项 HIGH 0 / MED 0`，`runServer` 仍然在启动期崩在
`EnchantmentMenuXpCostMixin`。**两个新注入点都是坏的**，审计一个都没报。

**规则**：`gradlew.bat build` 绿 + 审计全 OK **只代表「能编译、目标存在」**。
凡是新增/改动 mixin，交付前**至少**跑一次 `WLY_SELFTEST=1 runServer`（服务端类会被真实 transform）。
客户端 mixin（`client` 段）`runServer` 覆盖不到，要在验收清单里单独列「待游戏内验证」。


## 73. 「左键方块」用 `AttackBlockCallback`，不要自己加键位（症状标签：按键不灵）

**背景**：玩家反馈「手持铁锭恢复铁砧」这类功能**按键方案无法正常使用**。
`WlyKeys` 那套（`KeyMapping` + GLFW 直读）有三个天生短板：
容器界面里 vanilla 不分发 `setDown/click`、连续触发要靠手写节流、改键与其它模组撞车时静默失效。

**结论**：凡是「对某个方块做动作」的功能，**优先用原版已有的交互动作**，别新增键位。

| 动作 | Fabric 事件 | 取消方式 |
|---|---|---|
| 左键（攻击）方块 | `AttackBlockCallback.EVENT` | 返回非 `PASS` |
| 右键方块 | `UseBlockCallback.EVENT` | 返回非 `PASS` |
| 右键物品 | `UseItemCallback.EVENT` | 返回非 `PASS` |

**`AttackBlockCallback` 的行为（javap 反编译 Fabric 0.155.2 确认）**：

- 服务端注入在 `ServerPlayerGameMode.startBlockBreak`；客户端注入在 `MultiPlayerGameMode.startDestroyBlock`。
- 返回 `SUCCESS` → `cir.setReturnValue(true)` **取消破坏**，并由服务端补发
  `ClientboundBlockUpdatePacket` 让客户端撤销破坏动画。
- 客户端返回 `SUCCESS` 时还会走 `startPrediction(...)`，**仍然把 `START_DESTROY_BLOCK` 包发给服务端**
  —— 所以「两端都返回 SUCCESS」不会导致服务端收不到包。
- **本项目一律只在服务端处理，客户端返回 PASS**（与 harvest / reroll / beacon-fill 同口径）：
  专服与客户端配置可能不一致，客户端擅自取消会出现「点了完全没反应」的坏体验。

**交互设计铁律（本轮踩到的）**：判定条件里**只要有一项不满足就 PASS**，会让玩家
「手持铁锭、铁锭不够 → 左键 → 铁砧被挖掉了」。正确写法是把「是否接管」与「能否完成」分开：

```java
if (手上没铁锭) return PASS;              // 没带铁锭 → 交回原版（否则没法正常挖铁砧）
// ↓ 从这里开始：玩家已表达意图（拿着铁锭左键铁砧），绝不许原版把铁砧挖掉
if (铁砧已完好) return SUCCESS;            // 无反应，也不挖掉
if (铁锭不够) { 提示; return SUCCESS; }     // 只提示，不修复，也不挖掉
执行; return SUCCESS;
```

即「**只要玩家表达了意图（拿着铁锭点铁砧），就绝不让原版破坏发生**」。

**玩家口径会反复变**：v1.2.5 初版把「完好铁砧」判成 PASS（交回原版挖掉），
玩家随即要求「不要损坏铁砧的功能，完好铁砧时手持铁锭左键无效就行」→ v1.2.6 改成 SUCCESS 无反应。
**判定分支要按「玩家意图」而不是「功能是否可执行」来切**，前者才是稳定的。

**创造模式**：`player.getAbilities().instabuild` 时跳过 `shrink()`（手册 #67）。

## 74. 突破附魔上限后，原版钓鱼计时公式会结构性死锁（症状标签：失效）

**症状**：饵钓 ≥ 6 级的钓竿抛进水里**永远不咬钩**（浮漂只是漂着，从不出水花）。
玩家侧表现为「今天早些时候还能钓，给钓竿叠了附魔之后就不行了」。

**根因**（javap 26.1.2 / 26.2 同构，且已被运行时读数证实）：
`FishingRodItem.use` 里 `lureSpeed = (int)(EnchantmentHelper.getFishingTimeReduction() × 20f)`，
而饵钓**每级贡献 5.0** ⇒ `lureSpeed = 100 × 饵钓等级`。
`FishingHook.catchingFish` 的播种语句是 `timeUntilLured = Mth.nextInt(100, 600) − lureSpeed`，
`timeUntilLured > 0` 那条分支才会往下推进出 `timeUntilHooked → nibble`。
饵钓 ≥ 6 时该值**恒 ≤ 0** ⇒ 分支永不进入 ⇒ `nibble` 永远 0 ⇒ 永不咬钩。
原版最高只有饵钓 3（lureSpeed=300，roll 落在 301~600 时仍为正），所以这个坑原版碰不到——
是 `elb`（`AnvilMenuLevelMixin` 把 `getMaxLevel()` 重定向成 `Integer.MAX_VALUE`）把玩家送进了原版没设计过的区间。

**实测凭据**（自检 T17，反射构造 lureSpeed=800 的浮漂真调一次 `catchingFish`）：
兜底开 → 400 次里 `timeUntilLured` 最小 **1**；兜底关 → 最小 **−700**（=100−800，正是死锁值）。

**修法**：`@Redirect` 只改那一次掷点为 `max(roll, lureSpeed + 1)`，原版随后的 `− lureSpeed`
自然得到 `max(roll − lureSpeed, 1)`。饵钓越高咬钩越快（符合附魔语义），任何等级都不死锁。
`catchingFish` 内 `Mth.nextInt` 有**三处**，ordinal 必须数准：0=(20,40) nibble、1=(20,80) timeUntilHooked、
**2=(100,600) timeUntilLured ← 只改这一处**。

**规则**：
1. 凡是「突破原版上限」类功能（附魔等级、堆叠、倍率…），必须逐个检查**下游原版公式有没有定义域**。
   上限放开 ≠ 下游算式在放开后的区间里仍然成立。
2. **别拿猜出来的常数做排除结论。** 本轮我先按「饵钓每级 0.1」算出 lureSpeed=16，
   据此断言「附魔增加不是原因」——真实常数是 5.0（每级 100），结论完全反了。
   跨版本 jar 里读不出来的数值语义，只能靠**运行时读数**或**真跑一遍**，不能靠回忆。
3. 定位这类「判定链上不知道断在哪一环」的问题，加一条**只读诊断命令**把每道门打成 YES/NO，
   一次操作就定案；比逐个 mod 试错快得多（本轮 `/wly fish`）。

## 75. 反向锁要连「关掉模块必须重新变红」一起断言（症状标签：假绿）

T17 除了断言「开=最小值 ≥1」，还断言「关=最小值 ≤0」。
只断言前者的话，万一这条兜底根本没判在被交付的那条路径上（比如注入点选错、
或 `timeUntilLured` 其实被别处覆写），它也会恒报 ≥1 而**永远绿着骗人**。
**规则**：新加的行为类兜底，自检里必须成对写「开=修好」+「关=复现原缺陷」两条读数。

## 76. Mixin 注入的 handler 是独立方法，写不了目标类的 final 实例域（症状标签：致命/运行期崩）

**症状**：往 `FishingHook.<init>` 的 `@At("TAIL")` 注入 `this.lureSpeed = 5000;`，
编译过、`runServer` 也起得来，但**第一次创建浮漂就崩**：
```
java.lang.IllegalAccessError: Update to non-static final field
  net.minecraft.world.entity.projectile.FishingHook.lureSpeed
  attempted from a different method (handler$...$wly$saturateLureSpeed)
  than the initializer method <init>
```
**根因**：JVM 对「final 实例域只能在 `<init>` 里写」的校验是**按方法**判的。
Mixin 不是把语句内联进 `<init>`，而是生成一个独立的 `handler$xxx` 方法由 `<init>` 调用，
于是那条 PUTFIELD 的宿主方法不是 `<init>` → 校验失败。

**规则**：要改目标类的 final 字段值，**别去赋值，改它的来源**——
用 `@ModifyVariable(at = @At("HEAD"), argsOnly = true, index = N)` 改**构造参数的局部槽**，
真正执行 PUTFIELD 的仍是原版 `<init>` 自己。构造器里 `this` 占 slot 0，所以参数从 1 开始数
（`FishingHook(EntityType, Level, int luck, int lureSpeed)` → lureSpeed 是 **index 4**）。
`index` 必须自己按 javap 的参数顺序数，写错会静默改到别的槽（`argsOnly` 下 Mixin 不校验语义）。

## 77. `injection_audit.py` 看不见 `<init>` 目标，会误报 HIGH（症状标签：误判）

**症状**：`@ModifyVariable(method = "<init>(...)V")` 明明运行期绑上了（`require=1` 没崩、自检 PASS），
审计却报 `目标方法 <init> 在 ... 及其父类链上都不存在`。

**根因**：`ClassInfo.declares()` 用正则 `\b<名字>\s*\(` 在 **javap 文本**里找。
而 javap 打印构造器用的是**类的简单名**（`FishingHook(...)`），打印类初始化用的是 `static {};`，
两者都不含 `<init>` / `<clinit>` 字面量 → 按字面名查必然查不到。

**已修**：查存在前先把 `<init>` 翻成目标类的简单名、`<clinit>` 翻成 `static {};`。

**同时要知道这条护栏的边界**：`declares()` **只按方法名匹配，从不校验描述符**。
所以 `method="foo(II)V"` 指到只有 `foo(F)V` 的类上，审计也照样报 OK。
**描述符对不对，只能靠 `require=1` + 真跑一次**（本轮 T17 就是那个"真跑"）——
静态审计绿不等于注入绑对，见 #49 / #72。

## 78. i18n 漏键：`contains` 抽样式自检抓不到（症状标签：失效/显示裸键）

`en_us.json` 少了 `wly.module.anvil-no-limit`（英文界面直接显示键名），
而 T10 当时只做 `z.contains("key...sort") && e.contains("\"wly.module.big-stacks\"")` 这种**抽样**，
漏的恰好是没被抽到的那几个键 → 自检一直绿。

**修法**：T10 改成**逐键比对中英键集**：

```java
Set<String> onlyZh = new HashSet<>(langKeys(zh)); onlyZh.removeAll(langKeys(en));
Set<String> onlyEn = new HashSet<>(langKeys(en)); onlyEn.removeAll(langKeys(zh));
// 两者都必须为空
```

**规则**：只要两份文件是「同一套键的不同翻译」，自检就必须断言**键集相等**，
不能断言「某些键存在」。抽样式断言只在「允许两边键集不同」时才成立。

## 79. 给热路径加缓存，就必须把「失效点」一次列全（症状标签：改开关不生效）

**背景**：`ModuleManager.enabled(id)` 被 46 处 mixin 调用，其中 `SlotMaxStackMixin` / `ContainerMaxStackMixin` /
`ItemInstanceMaxStackMixin`（每次查堆叠上限）、`LivingEntityHurtMixin`（每次受击）、`PowershotMixin`（每次投掷）、
`LivingEntityClimbMixin`（每 tick 每实体）都是热路径。原实现每次调用都进
`WlyConfigData.ensureLoaded()` 的 `synchronized` 监视器，再做 `MODULES.get` + `STORE.getOrDefault` 两次哈希查找。

**改法**：首次解析后写入 `ConcurrentHashMap` 缓存；`WlyConfigData.ensureLoaded()` 本身也改为
`volatile loaded` 快路径 + `synchronized` 双重检查（慢路径只在首次装载时走一次）。

**坑（本条重点）**：缓存一旦加上，**所有能改变启用状态的入口都必须失效缓存**，漏一个就表现为
「配置界面点了没反应、重启游戏才生效」。本项目里这类入口有 4 个：

1. `WlyConfigData.put(id, v)` —— GUI 改开关（Cloth 的 `setSaveConsumer` 走这里）；
2. `WlyConfigData.reload()` —— 重新读配置文件；
3. `ModuleManager.forceOff(id)` —— 模块初始化抛异常被自动禁用；
4. 未来任何直接写 `STORE` 的新代码。

**验证**：自检 **T18** 做「改开关 → `WlyModule.on()` 立刻翻转 → 改回 → 复原」的成对断言。
只断言「能读到值」是假绿：缓存永不过期时，读到的仍是旧值。

## 80. 本机构建环境两个必踩的坑（症状标签：构建失败/找不到 java）

1. **`JAVA_HOME` 不在系统环境里**：本机 JDK 在
   `C:\Users\Administrator.DESKTOP-NEARQ8O\jdk25\jdk-25.0.3+9`（未注册到 `HKLM\SOFTWARE\JavaSoft`、不在 `PATH`），
   直接 `gradlew.bat build` 会报 `JAVA_HOME is not set and no 'java' command could be found`。
   跑构建/审计脚本前先 `$env:JAVA_HOME=...; $env:PATH="$env:JAVA_HOME\bin;$env:PATH"`
   （`tools/injection_audit.py`、`tools/mixin_audit.py` 需要 `javap` 在 `PATH` 上）。
2. **`TEMP`/`TMP` 是未展开的 8.3 变量**：某些会话里 `$env:TEMP` 的字面值是 `%USERP~1\AppData\Local\Temp`，
   Gradle 会把它拼成 `D:\C_migrated\appdata\gradle-home\daemon\9.5.1\%USERP~1\...` 并报
   `java.io.tmpdir is set to a directory that doesn't exist`。构建前把 `TEMP`/`TMP` 指向真实目录
   （如 `D:\AI\tmp\dsh-temp`）即可。这个错误与源码无关，别去翻代码。
